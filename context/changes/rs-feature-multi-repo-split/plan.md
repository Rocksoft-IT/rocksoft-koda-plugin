# Rs-feature picks the right client repository and splits multi-repo requests — Implementation Plan

## Overview
`list_repositories` now returns each repository's `role`, `description` and
`client` (Rocksoft-IT/n8n-hosting#159). `rs-feature` uses this to group a
client's repositories by `client` in Step 1, pick the obviously-matching one
by role/description without asking, and otherwise ask with role and
description shown. When one request needs work in more than one repository
of the *same* client, the skill agrees the split with the client, drafts one
cross-linked issue per repository tagged with a shared `feature` id (a UUID
generated once per request), and creates them — in a confirmed order, only
after one explicit "yes" — so the Cezar Pipeline can show them as one
feature.

## Current State Analysis
- `skills/rs-feature/SKILL.md:124-144` (Step 1) shows `list_repositories`'
  repositories as one flat numbered list (`name` + `description` only, no
  grouping) and always asks the client to pick when there is more than one,
  even when the request obviously names one of them (it only puts that one
  first and "recommends" it — `:133-135`).
- `skills/rs-feature/SKILL.md:146-179` (Step 2) already asks, once, which
  *configured* `related_repositories` (from `get_repository_context`,
  Rocksoft-IT/n8n-hosting#130) the request touches, and carries the answer
  forward as **touched repositories** (`:175-179`). It has no notion of
  repositories that are simply siblings of the chosen one in
  `list_repositories` — that signal (`client`) does not exist yet at this
  line.
- `skills/rs-feature/SKILL.md:229-257` (Step 5) already drafts one issue body
  per touched repository when there is more than one (`:238-245`), each with
  a `## Related repositories` section naming siblings by `name` only
  (`references/issue-template.md:46-49`); the footer comment
  (`references/issue-template.md:21`) carries `track`/`client`/`repository`
  only, no shared id across a batch.
- `skills/rs-feature/SKILL.md:258-321` (Step 6) proposes a deploy order,
  asks one combined "yes" for the whole batch, and calls
  `create_feature_issue` once per repository with
  `git_url`/`title`/`body`/`track`/`labels` (`:280-291`) — no field ties the
  batch together server-side; `docs/flow-contract.md:72-104` documents the
  same four-plus-labels input shape.
- `docs/flow-contract.md:43-47` documents `list_repositories`'s output as
  `{ repositories: [{ name, git_url, description }], email, count }` — no
  `role`, no `client`.
- The skill's own "Runtime assumptions" (`skills/rs-feature/SKILL.md:30-37`)
  rule out local files, shell, and git: any id the skill needs (the shared
  `feature` UUID) has to be generated by the model itself, as plain text, not
  by a tool call.
- `context/archive/2026-11-13-rs-feature-related-repos/plan.md` is the
  precedent for extending this exact "touched repositories" /
  draft-many/create-many machinery, and for the version-bump convention
  (`.claude-plugin/plugin.json`, `README.md` `## Wersja`, `USAGE.md`
  `## Wersja`, currently all at `0.4.0`).
- Rocksoft-IT/n8n-hosting#159 (the server-side field addition) and
  Rocksoft-IT/cezar#257 (the Cezar Pipeline grouping this feeds) are external
  repositories not present in this checkout; their exact shapes are assumed
  by symmetry with the fields `docs/flow-contract.md` already documents.

## Desired End State
- Step 1: with several repositories, they are shown grouped by `client`
  (one heading per distinct client, repos in it as `name` — `role` —
  `description`, every field shown only when present). A request that
  clearly matches one repository's role or description is picked without
  asking, with a one-line "picked `<name>` because …"; otherwise the client
  is asked, from the grouped list, never mentioning a repository not in the
  response. A server without the new fields behaves exactly as today.
- Step 2: the existing related-repositories question also offers, in the
  same single question, any other repository of the *same* `client` as the
  chosen one; the confirmed answer feeds the same "touched repositories" set
  as before. When that set ends up with more than one repository (from
  either source), the skill generates one `feature` id (UUID v4, its own
  text, no tool call) and carries it for the rest of the conversation. A
  single touched repository never gets a `feature` id.
- Step 5/6: unchanged for a single touched repository. For more than one,
  every drafted issue's footer and Metadata carry the shared `feature` id,
  and its `## Related repositories` lines name each sibling by role first
  (falling back to name when no role is known, e.g. a sibling that came from
  `related_repositories`). A same-client split may only combine repositories
  of that one client; `create_feature_issue` is called once per repository,
  in the confirmed order, now also passing `feature`.
- `docs/flow-contract.md` documents `role`/`client` on `list_repositories`
  and the new optional `feature` input of `create_feature_issue`.
  `.claude-plugin/plugin.json` (and the README/USAGE version footers) move
  to `0.5.0`.

### Key discoveries
- `skills/rs-feature/SKILL.md:175-179` already names and carries forward
  "touched repositories" as a single concept fed by one source
  (`related_repositories`); the same variable can take a second feed (same-
  `client` siblings) without new plumbing in Step 5/6.
- `skills/rs-feature/SKILL.md:271-279` (Guardrail 2) already allows
  `git_url` to be either a `list_repositories` entry or a named related
  repository — a same-client sibling is always a `list_repositories` entry,
  so no guardrail text about *targeting* needs to change, only the new
  same-client-only rule about which repositories may share one `feature` id.
- `references/issue-template.md:46-49`'s `## Related repositories` section
  already exists from the prior change; it only needs its line format
  extended to lead with role, not a new section.

## What we're NOT doing
- Changing anything inside Rocksoft-IT/n8n-hosting#159 (the directory server
  that now returns `role`/`client`) or Rocksoft-IT/cezar#257 (the Pipeline
  grouping by `feature`) — this plan only consumes and documents the
  contract those repos own.
- Re-opening the already-shipped `related_repositories` / configured-relation
  mechanism itself (Rocksoft-IT/rocksoft-koda-plugin#5): its own question,
  its allowance to target a repository the client isn't directly assigned to
  (AC-04 of that change), and its drafting/creation flow are reused, not
  rewritten. The "same client only" rule added here applies only to the new
  same-client-sibling source, never to that existing allowance.
- A tool to edit an issue after creation — cross-links stay plain body text
  filled in creation order, exactly as today.
- New README.md/USAGE.md prose about this capability — only their version
  footers move, per the project's existing precedent; the issue names only
  `docs/flow-contract.md` and `issue-template.md` for doc content.
- Any change to `references/tracks.md` — repository choice and the
  cross-repository split are track-independent, asked before Step 3.
- Validating the `feature` id's format or uniqueness server-side — that is
  the n8n workflow's concern, same as every other `create_feature_issue`
  input.

## Implementation Approach
A documentation/config-only plugin (`context/foundation/tech-stack.md`): no
code, no build, no tests to run. One increment, one area (the orchestrator's
`Areas:` block names a single A1, "builds on nothing"). Four phases follow
the conversation's own order and mirror the already-merged related-repos
change's phase shape: repository choice (Step 1), split discovery + id
(Step 2), draft + create (issue-template.md, Step 5, Step 6), contract docs +
version bump.

Two decisions worth recording explicitly:
1. **One unified "touched repositories" / one shared `feature` id,
   regardless of source.** Rather than add a second, parallel drafting path
   for same-client siblings, this plan feeds them into the exact mechanism
   Step 2/5/6 already have for `related_repositories`, and generates the
   `feature` id whenever that set has more than one entry — whether the
   second repository came from a configured relation or from being the same
   client. This keeps the skill's step descriptions from forking into two
   near-identical flows and gives the Cezar Pipeline one consistent grouping
   signal for any split, which fits `cezar#257`'s stated purpose better than
   limiting the id to only one of the two trigger sources would
   (decision-to-verify: this extends the already-shipped related-repos path
   slightly beyond issue #10's literal wording, for consistency).
2. **"Same client only" gates the new source, not the old one.** The issue's
   "Only repositories of the same client may be in one split" is scoped to
   the new same-client-sibling source; the pre-existing
   `related_repositories` allowance to target a repository the client is not
   directly assigned to (AC-04 of #5) is left exactly as it is, since
   narrowing it now would silently break an already-accepted behavior the
   current issue never mentions.

## Phase 1: Group repositories by client and pick by role
### Overview
Step 1 groups a client's several repositories by `client`, shows `role` and
`description`, and picks the one that clearly matches the request without
asking — otherwise it asks from the grouped list.

### Required changes
#### 1. Group and pick
- **File**: `skills/rs-feature/SKILL.md` (Step 1)
- **Goal**: When `list_repositories` returns more than one repository, group
  them by their `client` field (one heading per distinct client, in the
  order returned; a single client still gets its one heading) and show each
  repository as `name` plus `role` and `description` when present. When the
  request clearly matches exactly one repository's `role` or `description`
  (across the whole list), pick it without asking and say which one and why
  in one line. Otherwise ask the client to choose from the grouped,
  role/description-annotated list — never mentioning a repository the
  response did not return. A response with no `role`/`client` on any entry
  (older server) behaves exactly as today: flat list, always ask. The "one
  repository" and "none" cases are unchanged.
- **Contract**: `list_repositories` entries may now carry `role` (string)
  and `client` (string), both optional; `name`/`git_url` are still kept
  verbatim for every later call, and `role`/`client` are kept too, for Step 2
  and Step 5.

## Phase 2: Discover a same-client split and generate the feature id
### Overview
Step 2's existing related-repositories question also offers same-client
siblings from Step 1; once the touched set has more than one repository, the
skill generates the shared `feature` id itself.

### Required changes
#### 1. Combine same-client siblings into the existing question
- **File**: `skills/rs-feature/SKILL.md` (Step 2)
- **Goal**: Alongside the configured `related_repositories` already asked
  about here, also offer — in the same single question — any other
  repository from Step 1's list that shares the chosen repository's `client`
  value. Never offer a repository of a different client in this question.
  The confirmed answer (from either source) is still carried forward as
  "touched repositories", exactly as today; when neither source has a
  candidate, skip the question exactly as today.
- **Contract**: none (conversational; no new tool call — the candidate list
  comes from Step 1's already-fetched `list_repositories` response).

#### 2. Generate the feature id
- **File**: `skills/rs-feature/SKILL.md` (end of Step 2, once "touched
  repositories" is settled)
- **Goal**: When "touched repositories" has more than one entry, generate
  one `feature` id — a random UUID v4, as the model's own text, no tool call
  (per the Runtime assumptions: no local files or shell) — once per request,
  and reuse it for every issue drafted and created in this conversation. A
  single touched repository never gets one.
- **Contract**: none (conversational state, carried in-memory for the rest of
  the conversation; becomes a `create_feature_issue` argument in Phase 3).

### Success criteria
#### Automated
- [ ] `grep -qi 'same client' skills/rs-feature/SKILL.md`
- [ ] `grep -qi 'feature id' skills/rs-feature/SKILL.md`
- [ ] `grep -qi 'uuid' skills/rs-feature/SKILL.md`
#### Manual
- [ ] A read-through confirms a request touching exactly one repository never
      mentions a feature id and asks the related-repositories question
      exactly as before this change when there are no same-client siblings

## Phase 3: Draft and create split issues under one feature id
### Overview
`references/issue-template.md`'s footer, Metadata, and `## Related
repositories` lines carry the shared `feature` id and name siblings by role;
Step 5 fills them in, and Step 6 passes `feature` to every
`create_feature_issue` call of a batch, only ever mixing repositories of one
client in a same-client split.

### Required changes
#### 1. Issue template
- **File**: `skills/rs-feature/references/issue-template.md`
- **Goal**: Extend the footer comment (`:21`) with an optional trailing
  ` · feature: <uuid>` segment, present only when the draft is part of a
  multi-issue split; add a matching optional `**Feature:**` line to
  `## Metadata`, same rule. Change the existing `## Related repositories`
  line format (`:46-49`) to lead with the sibling's role when known
  (`**<role>** (\`<name>\`): <what changes>`), falling back to today's
  `**<name>**: <what changes>` when no role is known (e.g. a sibling that
  came from `related_repositories`, which carries no role field).
- **Contract**: footer/Metadata `feature` field is a UUID string, omitted for
  a single-repository request; `## Related repositories` heading and
  placement are unchanged.

#### 2. Draft with the feature id and role-aware naming
- **File**: `skills/rs-feature/SKILL.md` (Step 5)
- **Goal**: When drafting more than one issue (today's existing multi-draft
  logic, now also triggered by a same-client split), fill every draft's
  footer and Metadata with the shared `feature` id from Phase 2, and name
  each sibling in `## Related repositories` by role first per the template
  change above.
- **Contract**: no change to the drafting loop itself — same "print all
  drafts together, in deploy order" behavior as today.

#### 3. Create with the feature id, same-client only
- **File**: `skills/rs-feature/SKILL.md` (Step 6)
- **Goal**: Call `create_feature_issue` with a new `feature` argument — the
  shared id — on every call of a batch (omitted for a single-repository
  request, exactly as today). A same-client split (Phase 2's new source) may
  only combine repositories that share the primary's `client` value; this
  does not narrow the existing `related_repositories` allowance to target a
  repository the client is not directly assigned to (AC-04 of the prior
  related-repos change), which stays as it is. Deploy-order proposal, one
  combined "yes", cross-link filling in creation order, and mid-batch
  failure handling are all otherwise unchanged.
- **Contract**: `create_feature_issue(git_url, title, body, track, labels,
  feature?)` — `feature` optional, a UUID string, sent on every call of a
  multi-issue batch and omitted for a single issue.

## Phase 4: Document the contract and bump the version
### Overview
`docs/flow-contract.md` documents `role`/`client` on `list_repositories` and
the new `feature` input of `create_feature_issue`; the plugin version moves
to `0.5.0`, matching the project's version-bump precedent.

### Required changes
#### 1. Flow contract
- **File**: `docs/flow-contract.md`
- **Goal**: Add `role` and `client` (both optional strings) to
  `list_repositories`'s documented output shape, per-repository, alongside
  `name`/`git_url`/`description`; absence on either field means an older
  server (no grouping/auto-pick signal, same "missing is normal" convention
  already used for `files`/`missing`). Add `feature` (optional string, a
  UUID, present only for a multi-issue split) to `create_feature_issue`'s
  input table, and extend workflow step 4 ("dopisz blok metadanych, jeśli go
  brakuje") to also ensure `feature` lands in the created issue's footer when
  the input carried one.
- **Contract**: documentation only; no new skill-side tool call shape beyond
  Phases 1-3.

#### 2. Version bump
- **Files**: `.claude-plugin/plugin.json`, `README.md`, `USAGE.md`
- **Goal**: Ship this change as a new version, per the project's existing
  precedent (every user-visible change to the skill bumps `plugin.json` and
  both `## Wersja` footers).
- **Contract**: `version` field `"0.4.0"` → `"0.5.0"`; `README.md` `##
  Wersja` and `USAGE.md` `## Wersja` footer values move to `0.5.0` too.
